## 一、分工：谁负责什么

| 职责 | 归属 |
|---|---|
| 存待办、算 `deadline`、判断"到期" | **待办**（唯一权威） |
| 决定提醒的时机 | **待办** |
| 选台词、播动画、决定要不要游过来 | **桌宠** |
| 限频、去重 | **桌宠**（已实现） |

**为什么"到期"必须由待办判断**：桌宠再算一遍，两端时钟/时区/边界条件必然不一致，会出现"待办说超期了、桌宠说还没到"这种扯皮。桌宠只当表现层。

## 二、传输层

| 项 | 约定 |
|---|---|
| 通道 | Windows 命名管道 `\\.\pipe\whalechan-todo` |
| 编码 | UTF-8 |
| 分帧 | **单行一条 JSON**，`\n` 结尾 |
| 方向 | 双向（主要待办 → 桌宠） |
| 连接数 | 单客户端（桌宠） |
| 单条大小 | 建议 < 64 KB（待办通常只有几十条） |

**为什么不用 HTTP**：端口会触发 Windows 防火墙弹窗，管道不会；管道有 ACL，天然限制在当前用户，不用自己发 token。

**Go 侧起服务**（示意）：

```go
ln, err := winio.ListenPipe(`\\.\pipe\whalechan-todo`, nil)
for {
    conn, err := ln.Accept()
    go serve(conn)   // 一个连接，读到 EOF 就重来
}
```

> `winio` 指 `github.com/Microsoft/go-winio`。若不想引依赖，`net.Listen("unix", ...)` 在 Windows 上不可用，建议还是用 go-winio。

## 三、消息

### 3.1 桌宠 → 待办

```jsonc
// 连上后立刻发一次
{"type":"hello","from":"whalechan-pet","version":1}

// 用户点了菜单「看看待办」
{"type":"open"}
```

### 3.2 待办 → 桌宠

```jsonc
// ① 全量状态。连上后立刻推一次；之后任何变化（增删改、完成、改时限）都推一次。
{"type":"state","items":[
  {"id":"a2","content":"交周报","priority":"urgent","deadline":1792300000000,"completed":false},
  {"id":"a5","content":"整理桌面","priority":"minor","deadline":null,"completed":false}
]}

// ② 到期瞬间。同一事项只推一次。
{"type":"due","id":"a2","content":"交周报","priority":"urgent","overdueBy":0}
```

字段说明：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 待办唯一 id，用于桌宠侧去重 |
| `content` | string | 正文。桌宠会截到 24 字用于台词 |
| `priority` | string | `urgent` / `important` / `normal` / `minor` / `shelved`，**与 `meta.js` 的 key 一致** |
| `deadline` | number \| null | 毫秒时间戳 |
| `completed` | bool | 已完成的不提醒 |
| `overdueBy` | number | 已超期多少毫秒。刚到点传 `0` |

**`state` 推全量，不要推增量。** 几十条待办全量推的开销可以忽略，换来的是不用维护 diff、不用处理乱序、断线重连后自动对齐。

## 四、待办侧需要改什么

### 4.1 新增管道服务

建议新增 `pipe.go`（约 120–150 行）：

- `ListenPipe` + `Accept` 循环
- 维护当前连接的写入端（用 mutex 保护，多个 goroutine 可能同时想写）
- `Broadcast(msg)` 工具函数：序列化 + 加 `\n` + 写入；写失败就丢弃该连接
- 连接断开时清理引用，等下一个 `Accept`

### 4.2 三个推送时机

| 时机 | 推什么 | 位置建议 |
|---|---|---|
| 客户端连上 | `state` 全量 | `Accept` 之后立刻 |
| 待办数据变化 | `state` 全量 | `store.Save()` 之后统一触发（避免每个操作点都改） |
| 判定到期 | `due` 单条 | 现有的到期调度处（`isOverdue` 由假变真的那一刻） |

**关键**：`due` 只在"从未超期变成已超期"的瞬间推一次。不要在每秒的 tick 里反复推同一个事项——虽然桌宠侧有去重（同一事项每天最多 2 次），但重复推是浪费且会让日志变脏。

### 4.3 双模式

| 模式 | 启动 | 行为 |
|---|---|---|
| 独立模式 | 双击 exe | 现在的样子：有窗口、有吸附、**也照样起管道服务**（桌宠在就跑，不在就没人连） |
| 桌宠模式 | `--headless` | 无窗口、无托盘，只跑调度 + 管道推送 |

**建议：独立模式也起管道服务。** 这样用户不需要切模式，桌宠开着就会自动接上；桌宠没开时，管道没人连，开销为零。`--headless` 只是给"我不想看见那个悬浮窗"的用户准备的。

### 4.4 收到 `open` 时

把窗口显示出来并置前（如果当前是 `--headless`，则临时显示窗口）。这是用户点"看看待办"的响应。

## 五、桌宠侧已经做了什么（不用重复实现）

| 能力 | 实现位置 | 说明 |
|---|---|---|
| 管道客户端 | `src/main/todo-bridge.js` | 自动重连，指数退避上限 30s |
| 全量状态缓存 | 同上 | 断线后重连会自动拿到最新 `state` |
| 提醒去重 | 同上 | **同一事项每天最多 2 次**，落盘 `remind-state.json` |
| 台词分档 | 同上 | 五档优先级各一套台词；`shelved` 不提醒 |
| 心情联动 | 同上 | 心情 ≥70 才"游过来 + 做动作"，否则只冒气泡 |
| 静默降级 | `main.js` | 连不上时菜单里"看看待办"整项消失，**不弹任何错误提示** |

所以待办侧**不需要**考虑限频、去重、文案、动画——只负责"什么时候该提醒"和"提醒什么"。

## 六、容错约定

| 场景 | 期望行为 |
|---|---|
| 桌宠没开 | 管道无人连接，待办侧 `Accept` 阻塞，不影响任何功能 |
| 待办没开 | 桌宠侧静默重试，不报错、不占资源 |
| 待办崩溃 | 管道断开，桌宠侧检测到 `close` 并重连；待办重启后自动恢复 |
| 同时启动 | 谁先谁后都行，桌宠侧最多 30s 内接上 |
| 消息格式错误 | 双方都应忽略该行并继续，不要断开连接 |

## 八、联调方法

桌宠侧已用 Node 的 mock 服务端验证过协议（连接、全量状态、到期提醒、去重、断线重连均通过）。待办侧可以先不写 Go，用一段 Node 脚本当"假待办"来对：

```js
// 假待办：起管道、推一条到期事件
const net = require('net');
net.createServer((s) => {
  s.write(JSON.stringify({ type: 'state', items: [] }) + '\n');
  setTimeout(() => {
    s.write(JSON.stringify({
      type: 'due', id: 'test-1', content: '测试事项',
      priority: 'urgent', overdueBy: 0
    }) + '\n');
  }, 3000);
}).listen('\\\\.\\pipe\\whalechan-todo', () => console.log('假待办已监听'));
```

跑起来后，桌宠那边应该会说话。反过来，待办侧写好后用桌宠验证即可。
