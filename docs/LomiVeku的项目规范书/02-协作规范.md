# 02 协作规范（C 系列）

> 版本 v1.0｜2026-10-19｜适用范围：所有项目｜上位文件：README（十条铁律）

## 2.1 派单与归属

**C-01｜任务书四要素**：任务书必须写全目标（为什么做、做成什么样）、范围（允许改动的文件与目录）、验收（可判定的通过标准）、交付形态（产物路径与形态）。理由：缺任一要素，实施方只能自行猜测，猜测即偏差的来源，且偏差无法归责。落地：四要素缺一，实施方有权退回任务书，不得"先做再说"；补全后重新派单，批次号顺延。

**C-02｜一任务一归属、批次串行**：同一时刻，一个交付单元只允许一个实施责任人；并行的多个任务必须落在不相交的文件集合上；涉及同一交付物的批次必须串行，后一批等前一批过门禁并登记版本后才启动。理由：两人同改一份产物时后写者静默覆盖先写者，双方都以为改成了；批次并行则会让"这批的产物"无法界定，哈希与版本登记随之失效。落地：任务书首行写明责任人与批次号；一旦发生文件交集，后启动方即停手上报；启动新批次前核对前一批登记状态为"已通过"。

**C-03｜范围外只报不改**：实施中发现范围外的缺陷或可改进点，记录并上报，不在本批顺手修。理由：顺手修会把验收范围悄悄扩散，"这批已通过"这句话随之失去意义，返工时也分不清是谁引入的。落地：批报告固定设"范围外发现"栏，写明位置、现象、影响；未列入即视为未发现。修不修由主控另开任务。

**C-04｜建议前置实测**：对可见成果（界面、交互、产物形态）提出改进建议前，必须先完整跑一轮可运行的验证。理由：仅凭静态阅读或单张截图给建议，会把"看起来不对"当成"确实不对"，进而让实施方去修没坏的地方。落地：建议须附实测证据（命令与输出、或按流程取得的截图）；来不及实测的方向性意见必须显式标注"待实测校准"，未标注者不得作为决策依据。

## 2.2 变更与磋商

**C-05｜大改先磋商**：改动经 C-07 判定为 **L1 或 L2** 的，先出方向、再实施；触碰红线区的，无论级别一律先磋商。理由：方向错了，实施得越完整，返工越贵；而方向判断恰恰不需要完整实现就能做。落地：直接用 C-07 的分级作为"是不是大改"的可判定代理，不再另设"一眼可辨"这类主观描述；磋商在前（方向级意见可先给，标"待校准"）→ 实施一次到位（方向并入任务书，不做二次拆分）→ 验收在后（改完仍须完整跑测，不因"已磋商"而免检）。

**C-06｜冲突升级四条判定**：命中任一条即上交决策者，不得自行折中：①与已拍板需求直接冲突；②会改变已确认的交互语义；③纯偏好取舍、无客观判据；④触碰红线区或超出变更分级权限。理由：折中会把两个方案各自最差的部分组合起来，且事后无人对结果负责。落地：升级材料为"建议 + 原需求 + 冲突点"一页对照；未命中的普通分歧（可读性、一致性、规范对齐）由主控裁定，并在报告里写明理由。

**C-07｜变更权限分级**：按影响面把改动分三级——L1（须决策者明确指令，如结构调整、控件增删）、L2（可提意见申请，可多项合并统一审批，如设计体系级变量、全局参数、判据条款本身）、L3（自行决定，事后在批报告单列，如不涉重排的数值微调、间距对齐、新功能附带的新元素）。具体归类基线写进适配表。理由：分级把"要不要问"从感觉问题变成可判定问题，既避免事事上报拖慢节奏，也避免事事不问累积风险。落地：每批报告首段写"本批变更级别 + 依据条目"；L1/L2 同时触发 C-05 磋商与 C-06 升级判定，L3 免磋商但仍须批报告留痕；跨级操作视为越权，需回滚重走。

**C-08｜逐条回执**：对评审意见必须逐条回"并入 / 未并入 + 原因"，不得用"已处理""已优化"整体回复。理由：整体回复既无法定位漏项，也无法在事后追责——评审方看不出哪条被采纳，实施方也说不清哪条被拒。落地：回执表两列，左列原意见编号（不得改写），右列结论与理由；未并入项一并转给提出方，提出方有异议可再提一轮。

## 2.3 消息与凭证

**C-09｜长内容先落盘**：超过一屏的方案、报告、任务书，先写成文件再传递；消息正文只放摘要与文件路径，且**关键数字与结论必须写进摘要正文**，不得只写"详见附件"。理由：传输通道会截断、转义、丢消息，而文件是可复核、可哈希、可归档的唯一载体；摘要里没有结论，等于没传。落地：摘要缺关键结论视为未传递，接收方可直接退回。

**C-10｜消息即凭证**：消息 ID 与时间戳不得手打、不得回改；需要更正时补发一条更正消息并声明原消息作废。理由：凭证一旦被改写，事后就无法还原"当时到底说了什么"，争议将无法收敛。落地：证据文件命名含日期与来源标识；引用他方结论时附原消息 ID。

**C-11｜疑丢先取证**：怀疑消息丢失或未被读取时，先查会话日志、发送记录、对端回执三方核实，不凭猜疑重发。理由：重发会导致重复执行，比丢失更难收拾——重复的破坏性操作无法撤销。落地：核实结论写入报告；确需重发时标注"补发，原 ID 为 X"，并要求对端作废旧条。

## 2.4 上下文与交接

**C-12｜上下文健康双线**：设量化线与定性线，任一触发即主动提议切割会话。量化线为累计输入逼近适配表约定的阈值；定性线为出现"发沉"信号（需回读早前内容才能续写、响应变慢、回忆吃力）。理由：上下文超载的典型表现不是报错，而是"看起来还在工作，实际在编"——产出流畅但内容失真，且自查不出来。落地：切割提议权在任一方，决策权在主控；冷启动只带规则入口与当前状态，不带历史对话原文。

**C-13｜大对象隔离与截断**：整看类操作（全屏截图、全量日志、目录枚举、大体积结构化数据）一律交子代理或脚本处理，主会话只收"结论 + 关键数字 + 路径 + 异常清单"；列表类输出默认截断。理由：一次直读可瞬间吃光上下文且不可逆，代价是整段会话报废。落地：单条输出预计超过适配表设定的字符阈值即隔离；子代理不继承主会话记忆，纪律必须显式写进派单文本；主会话抽验至少核对关键数字与异常清单两项。

**C-14｜会话交接与冷启动**：交接包只含四样——当前状态、未完成项、规则入口（本规范与适配表路径）、复现命令。理由：历史原文信息密度低、携带成本高，且会把旧结论当成新事实带进下一轮。落地：接手方首轮必须能独立复现一次构建或一次测试，复现不成功即视为交接未完成。

## 2.5 复核与接管

**C-15｜复核不得橡皮图章**：复核必须独立取样、独立复跑，禁止直接采信实施方的结论与截图；批量对象按下限公式抽样，抽样触顶即升级为整批复核。理由：复核的全部价值在于"另一个人真的看了"，一旦变成盖章，整个门禁体系就只剩形式。落地：复核报告必须写"我实际执行了什么命令、看了哪些对象"，未覆盖的部分显式标注"未覆盖"，不得写成"已检查"。

**C-16｜故障接管须异源复测**：实施方的交付被判定为故障、由他人接管修复后，必须走一轮异源独立测试，不得以自检或自证替代。理由：接管者与被接管者往往共享同一套错误假设，唯有第三方能跳出来看。落地：接管报告须注明"复测方"与"复测结论"，复测未过不得重新交付。

**C-17｜需求变更走增量任务书**：执行中需求发生变化时，由主控出具**增量变更任务书**，按 C-01 四要素重列，并明确标注它取代原任务书的哪些要素。理由：口头改需求会让"这批做了什么"无法界定，验收与版本登记随之失真。落地：**已完成并通过验收的部分不作废**（基线保留，哈希锚定不动）；已实施未验收的部分由主控裁定保留或回滚，并在版本登记备注；未开工部分的原任务书要素自动失效。

**C-18｜送审基线必须冻结**：任何送审稿在发出前记录基线（时刻 + 全文件哈希），评审期间不得改动；确需修改的，另存为新版本号（如 rc2）并重新送审。理由：评审方批注的是"他读到的那一版"，基线一动，批注就失去指向，汇总时无法判断哪条意见仍然成立。落地：送审消息附基线哈希清单；必须中途修改时，先发"基线作废"通知，再发新版本。
