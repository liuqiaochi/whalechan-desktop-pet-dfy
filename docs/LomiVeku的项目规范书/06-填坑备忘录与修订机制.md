# 06 填坑备忘录与修订机制（M 系列）

> 版本 v1.0｜2026-10-19｜适用范围：所有项目｜上位文件：README（十条铁律）

## 6.1 为什么需要

团队真正稀缺的不是"解决问题的能力"，而是"不重复解决同一个问题"的能力。一个坑被填掉之后，如果没人写下来，它会在下一次换人、换会话、换项目时原样复现——而且往往由同样的人踩、用同样的方式排查、花同样的时间。

填坑备忘录的作用是把两条链路接通：**把教训变成规则**（可预防），**把有效做法变成惯例**（可复用）。它不是事故日记，也不是检讨书；判断一条记录有没有价值的唯一标准是——**下一个人读到它，能不能少踩一次**。

**M-01｜单一事实源**：同一个结论只在一处维护，其他文档引用而不复制。理由：复制会产生两个版本，改一处忘一处，最终没人知道哪份是对的。落地：规则正文放规范文件，事件细节放原始报告；备忘录只写结论与索引，不搬运原文。

## 6.2 怎么记

**M-02｜三行制**：每条记录固定三段——**事件**（现象、触发条件、影响面）、**处理**（怎么定位、怎么修、修完怎么验）、**沉淀**（以后怎么避免，指向哪条规则或哪个做法）。理由：只有"事件"会变成故事，只有"处理"会变成临时补丁，三段齐全才沉淀出可迁移的东西。落地：三段各自不超过三句；超出的内容外链到原始报告，不在此展开。

**M-03｜何时记**：四条触发，不设时限——①新坑处理完顺手提名；②测试或交付流程发生变化，同步更新规则章；③任一成员提议；④每个版本节点扫一遍"实操与规则的偏差"。理由：设时限（如"24 小时内必须提名"）会催生形式主义，而"顺手"才符合实际节奏。落地：提名只需一句话（什么坑 + 以后怎么规避），不要求完整成文。

**M-04｜提名 → 归档 → 通报**：提名一句话；归档时按三选一分流——能变成做法的进规则章加一条，是具体事件的进事件章加一条，一次性的不入档（留在原报告，最多留一行索引）；最后向相关方通报一句"记了什么、改了什么"。理由：三选一让"这条该去哪"有确定答案，避免规则章被事件淹没、事件章被口号污染。落地：涉他人技术结论时，归档前先向本人确认一句，避免转述失真；暂时定不了性的直接入档并标注"待确认"（写明已知事实 / 尚缺什么 / 谁能定），不另设待议区——"等结论明确了再记"通常意味着永远不会记。

## 6.3 收不收

**M-05｜收录三问**：①**会复发吗**（一次性笔误不收，系统性坑必收）；②**能变成做法吗**（不能就只留一行索引，不展开）；③**档案里已有吗**（有就并进去，不新开条目）。三问不要求全部答"是"——只要"会复发"成立就该收，哪怕暂时提炼不出规则。理由：把门槛设成"三条全过"，会让"知道会复发但还说不清怎么防"的坑进不来，而这类恰恰最该记。落地：答"不能变做法"的条目只保留索引，写明原始报告位置。

**M-06｜两条底线**：过时条目标注"已被 X 取代"并**保留**（保追溯）；内容重复的**合并成一条**而非并列（保精简）。理由：删除会让历史判断失去依据，并列会让同一个坑出现多个版本、互相矛盾。落地：合并时保留最早的事件编号，注明合并来源；被取代的条目不参与现行判定，但仍可检索；编号随版本重排时，引用以**条目标题**为准，并在文首声明重排。

**M-07｜修订记录表**：档案自身维护一张修订表，字段为：日期 / 版本 / 修订内容 / 原因 / 检验方式。理由：规则也会出错，没有修订记录就无法判断"这条规则是基于什么经验写的、还成不成立"。落地：结构性变更（增删章节）须告知相关方一句，日常条目增补不必走审批。

## 6.4 通用坑类清单

下表把反复出现的失败模式归为十类。用法：出问题后先归类，再按"通用对策"设计防护；新坑若归不进任何一类，才考虑新增类别。**M-K 是归类辅助，用于设计防护与检索，不构成判定依据**——判定仍按对应条款。

| 编号 | 坑类 | 识别信号 | 通用对策 |
|---|---|---|---|
| **M-K01** | 编码与宿主 | 同一文件在不同环境表现不同；中文路径或中文注释处失败；输出乱码、被截断在半句 | 链路 ASCII 化；字节级取证定案；写入端与读取端统一编码；比对前规范化 |
| **M-K02** | 坐标与度量 | 偏移量不是常数；换个屏幕/缩放就错位约一个比例；两组数字都对却对不上 | 显式声明坐标系与单位；读写同上下文；跨层换算并注释；断言名带口径后缀 |
| **M-K03** | 时序与竞态 | 偶发失败、重跑就好；机器忙时失败率高；"从未开始"被判为"已完成" | 轮询到截止替代固定等待；测两端点；设总预算；状态就绪守卫 |
| **M-K04** | 状态机缺口 | 某个异常路径后进入死状态；等待对方回应但对方不在；关闭/退出链卡死 | 穷举退化分支；错误态与空态分离；失败态阻断写入；幂等守卫 |
| **M-K05** | 资源与加载 | 文件存在、大小正常，但加载失败或用默认值；换了素材后行为突变 | 做加载级验证而非存在性检查；资源逐字节比对；期望值取运行时真值 |
| **M-K06** | 权限与归属 | 改动落在错误的副本上；用户文件被覆盖；多人同改一份产物 | 一任务一归属；只改点名的那一份；改前备份改后回读；跨副本同步须先问 |
| **M-K07** | 并发与单实例 | 双开抢资源、数据互踩；测试并行时随机失败 | 程序侧互斥；流程侧串行；显式等退出码；结束检查残留 |
| **M-K08** | 校验器自证 | 成批全红或全绿；差异数量异常整齐；换个脚本结论就变 | 先用已知好坏样本自证；怀疑工具优先于怀疑对象；集合比对先规范化；字节疑案看转储 |
| **M-K09** | 上下文与证据 | 会话后期产出失真；证据过期被当新证据；"没测"被读成"测过没问题" | 双线切割；大对象隔离与截断；证据带时刻与来源；报告单列未覆盖事项 |
| **M-K10** | 数据生命周期 | 读失败被当首次使用；空数据覆盖真实数据；升级/卸载丢配置 | 三态区分；失败态阻断写入；保留类断言；破坏性操作隔离 |

坑类与规则章的对应关系：M-K01 对应 E-01～E-03，M-K02 对应 E-05～E-07，M-K03 对应 T-12、E-08，M-K04 对应 E-15～E-16，M-K05 对应 T-02、D-03～D-04，M-K06 对应 C-02、S-01～S-03，M-K07 对应 T-13、E-09，M-K08 对应 E-10～E-12，M-K09 对应 C-12～C-13、T-15～T-16，M-K10 对应 E-16、S-07。

## 6.5 与外部规范的关系

本备忘录记录的是**项目踩过的坑及其抽象**，不替代通用规范：能直接对应到通用条目的，只在记录里引用编号，不重述内容；通用条目解释不了的，才在本档案里写完整推导过程。这样处理的好处是——通用规范升级时，本档案只需重审"引用关系是否仍然成立"，不必逐条改写。

## 6.6 本规范集自身的更新（v1.0：暂不设机制）

本版是首次落成，**不设定期复核、不预设修订流程**。理由：第一次落成时设计的更新规则，依据的是"还没真正用过"的想象，容易变成形式主义。

触发更新的信号有四类：① 出现归不进 M-K01～M-K10 的新坑类；② 某条规则在真实项目里被证明无法执行或与实操冲突；③ 项目适配表反复出现同一类偏离；④ 两条规则给出相反指令，且无法靠"取更严者"消解。

届时再按实际问题定更新规则（谁提名、谁裁定、怎么验证），不提前设计。在这之前，唯一生效的纪律是：**任何修改保留旧版并记录改了什么、为什么**。
