# 04 交付与发布规范（D 系列）

> 版本 v1.0｜2026-10-19｜适用范围：所有项目｜上位文件：README（十条铁律）

交付是"把构建产物变成用户能拿到的那个东西"的过程。它与测试的区别是：测试验证行为，交付验证**形态**——形态错误的产物，行为再正确也到不了用户手里。

## 4.1 交付形态

**D-01｜三种形态与 profile**：交付物归为三类——**目录型**（可执行文件 + 旁置资源目录，用于内部迭代）、**安装包型**（单个安装程序 + 校验清单 + 说明，用于对外分发）、**便携型**（压缩包 + 校验清单 + 说明，解压即用）。每种形态在体检脚本里对应一个 profile，profile 定义该形态的必需文件集合与额外检查项。理由：三种形态的失败模式不同（目录型怕资源缺失、安装型怕写入残留、便携型怕路径依赖），用同一套检查会漏。落地：适配表列明本项目产出哪几种形态、各自的目录与命名规则；新增形态必须同时新增 profile；该形态的必需文件集合缺失时判定 FAIL，**不回退到其他 profile 的集合**。

**D-02｜白名单零多余**：交付目录中除白名单文件外**不得有任何文件**——无测试数据、无日志、无缓存、无临时文件、无隐藏文件、无零字节文件。理由：多余文件不仅占体积，还会泄露内部信息、被误当资源加载、并在下一次比对时制造假差异。落地：白名单双向判定（缺一个 FAIL、多一个 FAIL）；允许存在但非必需的留档文件（如哈希清单）单列为 allowed_extra，不参与多余判定、不自我哈希。

**D-03｜资源与源码一致**：交付目录中的每一个资源文件必须与源码树中对应文件**逐字节一致**。理由：资源是最容易被"手工改一下"绕过版本管理的东西，一旦不一致，后续所有哈希与回归都建立在错误基线上。落地：逐文件哈希比对，不允许"大小相同""看着一样"作为通过依据。

**D-04｜产物含资源与版本信息**：构建产物必须携带运行所需的嵌入资源（图标、清单、元数据）与版本信息，不得以"裸二进制"形式交付。理由：这些属性不在源码里、不在资源目录里，只在构建那一刻被写入；构建脚本漏配时，程序照常运行，问题要到用户桌面上才暴露。落地：把"嵌入资源可被系统实际加载"作为独立检查项（见 D-06），而不是检查"构建参数里写了什么"。

**D-05｜哈希清单随产物交付**：每次交付必须生成哈希清单文件，覆盖全部交付文件（清单自身除外），并与产物放在同一目录。理由：没有哈希清单，接收方无法判断拿到的东西是否被中途改动或截断。落地：清单用统一格式（哈希 + 两个空格 + 文件名），按文件名排序，自身不计入；清单与说明等"允许存在但非必需"的文件统一记为 `allowed_extra`，不参与多余判定、不自我哈希（与 D-02 同一机制）。

## 4.2 交付三查

**D-06｜交付三查**：放行前必须完成三项独立检查——①**资源实测**（把嵌入资源真正加载一次，而不是查文件是否存在）；②**一致性比对**（交付目录 ↔ 源码树逐文件哈希）；③**从交付位复跑**（在交付目录里运行自检，而不是在构建目录里运行）。理由：三项分别拦三类逃逸——资源没进去、资源是旧的、跑的不是这一份。落地：三查结果逐项写入报告，任一项缺失即视为未交付。

**D-07｜命令即门禁**：所有确定性检查必须收敛为**一条命令**，清单内容全部实现在脚本里；日常只跑脚本读反馈，不靠人回忆清单。理由：需要"记得做"的检查，执行率随项目疲劳度线性下降；而脚本化后人工成本恒定为一条命令，且不会漏项。落地：适配表登记门禁命令原文；报告附命令与完整输出，不接受"我跑过了"。

**D-08｜退出码语义统一**：`0` = 通过；`1` = 失败（任一检查项为假）；`2` = 参数或环境错误（路径不存在、依赖缺失）；`3` = 部分完成（存在被跳过项）。理由：退出码是脚本与流水线之间唯一的机器接口，语义含糊会让"跳过"被当成"通过"。落地：任何自定义检查脚本都必须实现这四态；`2` 与 `3` 不得折算成 `0`。

**D-09｜PARTIAL 不放行**：存在跳过项的结论一律视为未通过，不得放行；确需放行必须由决策者显式豁免，并在报告中写明"哪些项未验证、风险由谁承担"。理由：跳过项恰恰是最难验证、最可能藏问题的那些，把它们从分母里去掉，等于用"少测"换"通过率"。落地：豁免需写明生效范围（仅本批次）与失效时间，不得写成长期许可。

**D-10｜互不加项**：功能自检管"产品行为对不对"，交付体检管"产物形态对不对"，两者不得因"顺手"互相塞项。理由：自检的语义一旦被形态检查污染，就无法再从"自检全绿"推断产品健康；而清单膨胀的代价是执行率下降。落地：新增检查项时先回答"这属于行为还是形态"，答不出就不加；跨类需求改为在对方脚本里新增，不改语义。

**D-11｜新增检查项须异源检验**：任何新增或修改的检查项，必须先由**非作者**用"已知好样本必通过 + 已知坏样本必失败"双向验证，通过后才可启用；新增项只做一遍完整执行，其余时间直接调用。理由：检查脚本自身也是代码，也会有 bug；未经检验的检查项会制造假失败（浪费返工）或假通过（放过缺陷），后者更贵。落地：脚本头部维护清单版本号；变更记录写"改了什么、谁验的、验的样本是什么"。

## 4.3 三个边界

**D-12｜一致性 ≠ 完整性**：交付目录与源码树一致，只证明"两份相同"，不证明"源码树本身没被改过"。理由：若源与被交付物同时被改动，一致性检查拦不住——这是设计边界，不是缺陷。落地：必须再配合一个外部锚点（构建输出哈希或验收基线），把交付物锚定到某个已知状态；报告中明写"本次一致性检查的基准是什么"。

**D-13｜自证 ≠ 他证**：用产物自己的自检证明产物正确，只能证明"这个产物认为自己对"，不能证明"它就是期望的那个产物"。理由：版本号可以被构建参数伪造，自检代码也可以随产物一起错。落地：必须有独立于产物的哈希锚定（D-14），且锚定值记入版本登记。

**D-14｜哈希锚定**：交付物的哈希必须与构建输出记录的哈希相等，基准值写入版本登记表；未提供基准值时该检查项标为"未启用"，不得标为"跳过"或"通过"。理由：这是唯一能拦住"资源对、版本对、代码是旧的"这类缺陷的机制。落地：哈希基准与构建批次一一对应；重新构建即产生新基准，旧基准作废但保留记录；未提供基准值时该检查项标为"未启用"，**不计入判定分母、不影响 PASS/FAIL，也不产生 SKIP**——否则尚未建基线的新项目会永远停在 PARTIAL。

## 4.4 版本与归档

**D-15｜内部版与对外版分离**：维护两套互不干扰的编号——**内部版**用于迭代管理与问题追溯，**对外版**用于用户可见的品牌化版本号。两者由同一份代码在构建期分别注入，不得为了对外好看而改动内部编号，也不得把对外编号用于内部登记。理由：内部编号承担追溯职责，一旦被"美化"，历史批次就无法排序。落地：构建脚本按 profile 分别生成，互不污染；报告中同时写明两个编号。默认口径：对外版**独立编号、不随内部版自动递增**；每次对外发布由决策者指定对外版本号，内部版继续按自己的节奏递增，两者只在发布记录里建立对应关系。无对外发布的项目，本条不适用。

**D-16｜补丁位与次版本位**：修缺陷与不改变功能语义的微调走补丁位（+0.0.1）；新增功能、既有功能升级、结构性调整走次版本位（+0.1.0）；升次版本时补丁位清零。归类存疑时提请决策者追认并在登记表备注。理由：版本号是给未来的自己看的索引，规则含糊会让"这次改了多少"无从判断。落地：每个批次在报告中写明"本次版本动作 + 归类依据"；并行批次（C-02 允许的不相交文件集）合并交付时，版本动作一次性计合计变更，各批报告分别注明自己承担的部分。

**D-17｜主版本评估（可选启用）**：若项目启用主版本评估，按事件计数而非时间触发——设若干事件类别与阈值，命中"各类同时达标"或"合计达线"时提醒决策者评估是否升主版本；计数只在主版本升级后清零，与补丁位清零互不相干。评估权归决策者，任何自动升级都必须是决策者事先明确授权的特例。理由：主版本代表"用户需要重新理解这个产品"，这个判断不能由计数器代替。落地：计数快照随批次报告输出；归类存疑的事件不计数，先提请追认。

**D-18｜旧版先归档再替换**：替换交付目录中的旧版本前，必须先把旧版打包归档，归档名含**时间 + 内部版本号**，存入历史目录；不得直接覆盖。理由：覆盖是不可逆操作，而"回退到上一版"是发布后最常见的需求。落地：归档包必须可解压且能被独立校验；归档完成后才允许替换。

**D-19｜版本登记表**：每次交付在登记表新增一行，字段为：内部版本 / 期段 / 内容摘要 / 产物与哈希 / 去向 / 状态。状态取值限定为"已交付""已归档""已取代""已撤回""已回退"，不得自造状态词。理由：登记表是唯一能回答"线上这一份到底是什么"的地方，字段缺失等于无法追溯。落地：登记行与产物一一对应；被取代的行保留并标注取代者，不得删除。

**D-20｜命名与文档一致**：报告、说明、登记表中引用的文件名必须与产物**逐字一致**（含分隔符、大小写、扩展名）。理由：一个短横线的差异就足以让人拿错文件，而这类错误在人工核对时几乎不可见。落地：门禁中加入命名核对项；产物改名即视为新产物，须重新走三查。

**D-21｜回退流程**：已发布版本发现缺陷需要回退时：①由决策者批准；②用 D-18 的归档包恢复，不得现场重构一个"看起来一样"的版本；③版本登记新增一行，状态写"已回退"，并注明回退到哪一版；④用户数据一律不动（S-07）。理由：回退是发布后最常见的需求，没有流程就会临场发挥；而"现构一个旧版"既不可复现，也无法证明与当时一致。
